# 매회 Pod 준비를 한 명령으로 실행

## 수동으로 먼저 할 일

- RunPod에서 GPU와 검증 템플릿 `runpod/pytorch:1.5.0-cu1281-torch280-ubuntu2404`를 선택한다.
- HTTP 8888,8000과 SSH TCP 노출을 **설치 전에** 설정한다.
- `runpod_esg.pub` 공개키를 등록하고 SSH 서비스를 준비한다.
- Mac에서 해당 새 주소에 직접 SSH로 접속해 서버 지문을 확인한다. 자동화는
  `StrictHostKeyChecking=yes`를 사용하며 지문 확인·키 등록을 우회하지 않는다.

Pod 생성/Start/요금 결제, SSH 키 등록, Render/Vercel 설정 변경은 이 스크립트가 수행하지 않는다.

## Mac에서 실행

이 저장소 루트로 이동해 실행한다. 추가 Python 패키지는 필요 없다.

```bash
./runpod up --ssh 'ssh root@새IP -p 새포트 -i ~/.ssh/id_ed25519'
```

`--ssh`에는 Connect의 **SSH over exposed TCP** 명령을 그대로 붙여넣는다.
콘솔의 -i 경로 대신 이 프로젝트에서 검증한 `~/.ssh/runpod_esg` 키를 기본으로 사용한다.
다른 키를 의도적으로 쓰려면 `--identity /키경로`를 지정한다. 키 자체는 전송하지 않는다.

다른 Mac/새 clone의 최초 실행에는 기존 비공개 백업을 지정한다.

```bash
./runpod up --ssh 'ssh root@IP -p PORT' --backup /로컬경로/ai-slop-rescue-4090-20261103.tar.gz
```

실행 내용:

1. SSH 및 기존 API 상태 확인. 이미 정상 실행 중이면 코드 덮어쓰기·설치·재시작을 하지 않는다.
2. 새 환경에는 로컬 저장소의 **커밋된 HEAD**에서 GPU 코드만 업로드한다.
   로컬 미커밋 파일·브라우저 코드·개인키는 업로드하지 않는다.
3. 백업의 worker.env와 요청 원장을 **없는 경우에만** 복원한다. 기존 키·원장은 덮어쓰지 않는다.
4. Python/PyTorch 확인. 4090은 Qwen INT8, 5090은 BF16 선택. FLUX 생성 모델은 BF16 유지.
5. 고정 패키지 설치, 모델 다운로드/로딩, 워밍업, GPU API 백그라운드 실행.
6. 인증된 내부 health 확인, 일관된 SQLite 원장·설정·코드의 비공개 로컬 백업.
7. 외부 HTTPS 인증 확인, Render에 넣을 GPU_API_URL 출력. 자동으로 실제 이미지 생성 요청을 보내지는 않는다.

백업·마지막 연결 정보는 `.runpod/`에 보관하며 Git에서 제외된다.
마지막 성공한 백업은 다음 Pod에서 자동으로 사용한다. 이 폴더도 필요하면 별도 개인 저장소에 백업한다.
백업에는 API 키와 원장 속 이미지가 포함될 수 있다. 공개 공유하지 않는다.
기본 백업은 모델 캐시를 포함하지 않아 새 Pod에서 모델 다운로드 시간은 다시 든다.
`up` 완료 전 최신 사용자 요청이 있다면 종료 전에 다시 backup을 실행한다.

## 이후 짧은 명령

```bash
./runpod up          # 마지막 주소로 준비/재개. 건강한 서버는 재시작하지 않음
./runpod status      # 설치 단계·내부 health 확인
./runpod logs        # 모델/API 로그 마지막 60줄
./runpod logs --setup  # 패키지 설치 로그
./runpod copy-key    # 키를 터미널에 출력하지 않고 Mac 클립보드로 복사
./runpod backup      # 종료 전에 로컬 백업 + SHA256 확인
```

Pod ID가 바뀌면 출력된 URL을 Render GPU_API_URL에 적용한다. 백업에서 같은 키를 복원했다면
API 키는 유지한다. 새 키가 생겼다면 copy-key로 복사해 Render GPU_API_KEY도 갱신한다.
Render 변경은 사용자가 직접 진행한다.

## 실패·재실행

- SSH 연결 거절/키 인증/지문 오류: Connect 정보와 SSH 설정을 직접 확인한다. Pod를 자동 생성·시작하지 않는다.
- 포트 8000이 열려 있는데 인증 health가 실패: 기존 프로세스를 종료하지 않고 중단한다. logs로 확인한다.
- 설치 중 다시 실행: 실행 중인 준비 프로세스가 있으면 기다리며 중복 설치/시작하지 않는다.
- 설치 단계가 실패: 로그를 확인한다. 스크립트는 생성 API 요청을 자동 재시도하지 않는다.
- 기본 대기 상한은 900초다. 초과해도 원격 설치를 죽이지 않는다. status/logs로 확인한다.
- GPU 검증 완료 기준: 이 스크립트의 health 외에도 별도 실제 생성·판정·에너지·품질 시험이 필요하다.

## 검증 상태 (2026-11-03)

로컬 테스트로 healthy 서버 보존, 점유 포트 보호, 오래된 설치 상태 처리, 기존 키·원장 보존,
백업 무결성을 확인했다. 사용자가 Pod를 정지해 두었으므로 새 자동화의 실물 전체 설치 시험은
다음 회차로 보류했다. Pod를 켜거나 새 유료 리소스를 생성하지 않았다.
