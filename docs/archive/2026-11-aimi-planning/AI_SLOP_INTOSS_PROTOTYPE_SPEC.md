## 1. 제품 범위와 변경 사항

AIMI는 게임 기록으로 확보한 예산을 사용해 목표 이미지의 조건과 모델을 선택하는 학습형 미니앱이다. 별도로 프롬프트 개선과 공개 지표 기반 모델 추천을 제공하며, 활동으로 받은 EP는 정원 아이템과 캐릭터 구매에 사용한다. 배포 목표는 앱인토스다.

| 항목 | 최신 기준 |
|---|---|
| 핵심 기능 | 일일 게임 + 이미지 챌린지 / 프롬프트 개선기 / AI 모델 추천 / 정원·상점·소셜 |
| 게임 3종 | 길 건너기형, Temple Run형, 크롬 다이노형. 슈퍼펭귄형 대체 |
| 게임·챌린지 횟수 | 각각 하루 최대 5회, 별도 카운터 |
| 챌린지 키워드 | 분류·카드 상자·개별 가격 없이 텍스트 목록으로 선택 |
| 챌린지 조합 | 선택한 키워드 해제·순서 변경, 자동 문장 조합, 저성능/고성능 선택 |
| 결과 | 사전 제작 이미지 + 조건 점수 + 모델별 통과 기준. 성공/실패는 팝업 |
| 모델 추천 | 업무에 따른 Light/Medium/High 추천 → 등급 하단 시트 → 개별 모델 상세 |
| 모델 상세 | 종합 성능·속도·입출력 100토큰당 단가·업무 관련 지표·출처 |
| EP 사용처 | 정원 아이템, 캐릭터. 게임 테마·맵 테마 판매 제외 |
| 캐릭터 | 여러 개 소유 가능, 정원과 모든 게임에는 선택한 한 캐릭터만 적용 |
| 친구 | 자체 친구 코드·미니앱 초대·친구 정원 및 공개 챌린지 상태 |
| 디자인 | 밝은 Light 배경, 공통 간격, 앱인토스 내비게이션, 플로팅 탭, 결과 팝업 블러 |

**제외:** 피트니스·건강 연동·운동 직접 입력·OCR, Chrome 확장 프로그램·외부 채팅 사용량 수집, 영수증·프린터·자전거, 실제 전력·탄소 절감량, 게시판·채팅·랭킹, 현금성 포인트, 실시간 이미지 생성·CLIP 서버, 글·동영상 목표, 챌린지 자유 입력. 기존 캠페인 프로젝트와 DB·배포를 변경하지 않는다.

### 2.2 주요 흐름

1. 토스 로그인 또는 기존 세션 복구 → 홈에서 오늘 게임·EP 조회.
2. 오늘 목표 확인 → 게임 플레이 → 서버가 기록·모은 EP·최고 점수 확정.
3. 종료 팝업에서 재시도 또는 **이미지 챌린지 도전하기**.
4. 목표를 보며 키워드 선택 → 조합 확인에서 순서·자동 문장·모델·비용 확인 → 제출.
5. 성공/실패 팝업 → 확인 또는 재시도. 일반 실패는 선택 초기화·예산 복구·횟수 소모.
6. EP로 정원 아이템·캐릭터 구매 → 정원 저장 → 친구 정원 방문.

개선기·모델 추천은 홈에서 각각 독립 진입한다. 개선기 결과의 **모델 추천받기**는 선택·편집한 최종 문장과 분석 ID를 전달한다. R01의 직접 입력 경로도 유지한다.

## 3. 공통 UI 구현 기준

- 기준 캔버스 375×812. 실제 구현은 반응형이며 기기 안전 영역·키보드·가변 높이를 적용한다. PDF의 휴대폰 테두리·9:41·상태바·홈 인디케이터는 앱 콘텐츠로 복제하지 않는다.
- 앱인토스가 제공하는 상단 내비게이션을 사용한다. 자체 뒤로가기·닫기를 중복 배치하지 않는다. 게임 일시정지는 게임 안의 제어다.
- 탭: 홈 / 미션 / 정원 / 마이. 공식 플로팅 형태를 기준으로 한다. 모든 세부 화면에 무조건 탭을 붙이지 않는다.
- 밝은 연두색 Light 배경. 배경 효과는 CSS로 구현하고 텍스트·입력 대비를 확인한다. 정원 예시 영역은 **불투명 단색 #4F783F**, 안쪽 바닥 상자 없음, 흰 제목.
- 실제 제품의 폰트·컴포넌트는 앱인토스 SDK/TDS 지원 방식을 확인해 사용한다. Figma 로컬 편집본은 TDS 원격 컴포넌트 인스턴스가 아니며 Noto Sans KR 사용은 전달용이다.

| 간격 토큰 | 논리 px | 적용 |
|---|---:|---|
| pageMargin | 24 | 일반 화면 좌우 |
| titleContent / fieldResult | 16 | 제목 다음 콘텐츠, 입력 다음 결과 |
| copyList | 12 | 설명 다음 목록 |
| peer | 8 | 동급 요소·관련 문구 |

| titleDescription | 8 | 소제목 다음 설명 |
| primaryButton | 높이 56, 반경 16 | 기본 CTA |

출석·팁 팝업에도 같은 규칙을 적용한다. 게임 종료·챌린지 결과는 같은 팝업 컴포넌트·기준 위치를 사용한다. 실제 이전 화면에 블러를 적용하며 밝기를 낮추는 어두운 딤을 기본으로 넣지 않는다. PDF 캡처 이미지를 앱 배경으로 사용하는 방식은 피한다. 접근성·성능이 부족한 기기는 밝은 불투명 배경으로 대체한다.

키워드는 모바일에서 줄바꿈되는 텍스트 버튼 목록으로 제공한다. 작은 글자를 억지로 3열에 고정하지 않고 충분한 터치 영역을 확보한다. 선택은 색·밑줄과 상태 속성으로 표시한다. 항목별 상자·분류 탭·가격 표시는 없다. 조합 화면에서는 선택된 항목을 칩으로 보여줄 수 있다. 길게 눌러 정렬하는 방식 외에 순서 이동 버튼도 제공한다.

3D가 최종 필요하면 Three.js 계열을 검토하되 Phaser와 동시에 기본 엔진으로 도입하지 않는다. 현재 PDF는 2D 목업이며 엔진 선정 완료를 의미하지 않는다. 정원도 동일 캐릭터 이미지·스프라이트와 2D 좌표 배치를 재사용하는 구성이 초기 개발에 적합하다.

상시 GPU·CLIP·Redis·실시간 소셜 서버·Capacitor·Apple Developer 계정은 현재 구성에 필수 아님. 미니앱 본체는 앱인토스 배포 경로를 사용한다. Supabase는 DB/Storage 역할이며 이메일 인증을 위해 Supabase Auth를 필수 도입하지 않는다. 유료 플랜은 트래픽·백업·상시 운영 조건 확인 후 선택한다.

## 5. 게임·예산·EP 규칙

### 5.1 확정 규칙

- 오늘 제공되는 게임은 한 종류. 공개 일정에 게임 유형을 저장한다.
- 게임 최대 5회/일, 이미지 챌린지 최대 5회/일. 서버 날짜는 Asia/Seoul.
- 기록 → 당일 게임 예산, 경로 수집물 → EP. HUD는 **모은 EP**로 표시한다.
- 예산은 게임 자원이며 실제 토큰·전력·현금이 아니다. EP는 현금성·토스 포인트가 아니다.
- 게임을 잘해서 받은 예산 차이는 보정하지 않는다.
- 모든 게임에 선택된 한 캐릭터를 적용한다. 캐릭터 구매가 능력치 차이가 되지 않도록 한다.
- 전체 화면 플레이, HUD·일시정지·나가기만 제공. 하단 설명용 흰 상자 없음.
- 종료 팝업: 남은 횟수, 이번 모은 EP, 게임 스코어, 현재까지 BEST, 재시도, 이미지 챌린지 도전하기.

조작: 길 건너기는 탭 전진, Temple Run형은 좌우 스와이프 회피, 다이노형은 탭 점프. 조작 문구를 게임 화면 하단 카드로 상시 표시하지 않는다. 최초 짧은 안내는 별도 상태로 처리한다.

### 5.2 개발용 기본 정책 제안 — 아직 확정 아님

| 정책 | 제안 |
|---|---|
| 기록 집계 | 오늘 승인된 최고 기록. 5회 누적으로 예산을 부풀리지 않음 |
| 예산 함수 | game_version별 단조 증가 함수 + 최소/최대. 최소 예산으로 검수된 성공 조합 하나 가능 |
| 예산 이월 | 없음. EP·구매품은 유지 |
| 중단 | 시작 승인 시 1회 예약, 앱 이탈은 일시정지. 같은 play_id 복구, 중복 시작 금지 |
| 성공 후 게임 | 남은 게임은 가능, 새 기록·코인 EP 반영. 이미 지급한 성공 보너스 소급 증액 없음 |
| 자정 | 새 플레이는 새 날짜. 기존 플레이·제출은 시작일 버전에 귀속, 제한된 유예 후 만료 |

중단 복구 시간·자정 유예·예산 환산·코인 상한은 테스트 전 값이 필요하다. 하드코딩하지 않고 버전 정책으로 둔다.

### 5.3 성공 EP 및 일일 보상

```text
remainingBudget = approvedBudgetAtSubmit - keywordCost - modelCost
successEP = baseEP + floor(remainingBudget * bonusRate)
```

절대 잔량 기준이며 비율 보정 없음. 최초 성공에 한 번 지급하는 정책을 제안한다. 예시: 기본 20, 계수 0.1, 예산 120·비용 42이면 27 EP. PDF의 출석 +5, 팁 +3, 캐릭터 80 EP 등도 **UX 예시**이며 최종 경제표는 별도 확정한다.

코인, 성공, 출석, 팁 확인, 개선기 첫 체험의 보상 유형을 각각 둔다. 팁 보상은 팝업 확인으로 요청하고 단순 재열람에는 재지급하지 않는다. 개선기 체험은 유효한 처리 성공 시 하루 한 번 지급하는 안이다. API 오류로 보상을 얻지 못한 재시도는 중복 지급되지 않아야 한다.

## 6. 이미지 챌린지 엔진

### 6.1 입력과 화면

- 시작 전·키워드 선택·조합 확인에서 목표 이미지 확인 가능. 목표 확대는 닫을 수 있는 미리보기.
- 의미가 다른 후보를 충분히 제공한다. PDF 예시 30개는 데이터 예시이며 고정 개수가 아니다.
- 목록에서 선택·해제 → 조합에서 순서 변경·해제 → 자동 문장 미리보기. 직접 수정·추가 입력 없음.
- 목록에 개별 가격을 노출하지 않아도 내부 카드 비용은 존재한다. 조합 화면에 키워드 합계·모델 비용·총비용·잔액을 명확히 보여준다.
- 모델 선택은 저성능/고성능 2종. 모델 추천 화면의 Light/Medium/High 3등급과 별개다.

### 6.2 조건·문장·이미지의 공통 데이터

```text
keyword: id, label, semanticTags, entityBinding, conflictGroup,
         cost, orderingRole, phraseTemplate, contentVersion
condition: id, expectedValue, weight, required, omissionRule, wrongValueRule
modelOption: id, tier, cost, passThreshold
variant: id, actualConditions, allowedInputProfiles, modelTier,
         imageAssetId, reviewStatus, ruleVersion
```

범주·의미 태그는 내부 평가·제작용으로만 유지한다. 선택 순서를 반영하되 관계 대상을 바꾸는 잘못된 문장이 생성되지 않도록 슬롯·관계 문법을 검증한다. 사용자 제출 시 LLM을 불러 문장을 만드는 대신 검수된 템플릿·결정적 조합 코드를 사용한다.

### 6.3 판정

```text
score = clamp(sum(satisfiedConditionWeights) - definedPenalties, 0, 100)
pass = requiredConditionsMet && !blockingConflict && score >= model.passThreshold
```

고성능은 더 비싸고 통과 임계값이 낮다. PDF 예시는 저성능 12 예산·85점, 고성능 40 예산·70점. 이는 학습 게임의 가정이며 실제 모델 측정값이 아니다. 오지정·누락·충돌 감점과 필수 조건은 과제별 버전으로 저장한다. 고성능도 필수 대상 오류를 자동 정답 처리하지 않는다.

LLM이 점수를 실시간 결정하거나 텍스트 임베딩 0.8을 80점으로 표시하지 않는다. 조건 ID 매칭이 판정 기준이다. 임베딩·LPIPS·이미지 임베딩은 제작 시 후보 검색·유사 이미지 군집화의 보조 도구이며 요청 경로에 필수로 두지 않는다.

### 6.4 결과 이미지 매칭과 오류

선택 조건을 정규화한 profile + 모델 등급으로 검수된 대표 이미지를 찾는다. 핵심 대상·개수·관계가 다른 결과를 유사하다는 이유만으로 반환하지 않는다. 이미지 커버리지는 과제 발행 전 확인한다. 모든 조합을 생성하는 대신 승인된 조건군으로 묶되, 매칭 불가 시 `RESULT_VARIANT_UNAVAILABLE` 시스템 오류로 처리한다.

일반 실패: 횟수 1 소모, 비용은 최종 차감하지 않음, 재시도 시 선택·모델 초기화. 성공: 비용 확정·첫 성공 EP 지급. 시스템 오류·이미지 미매칭: 횟수·예산 유지. 최종 시도 소진 후에는 재시도 버튼을 비활성화하고 다음 미션 안내를 제공한다.

점수·통과 기준·조건별 피드백은 서버에서 반환한다. 결과 이미지는 사전 제작 예시임을 필요한 설명에서 안내한다. 성공 팝업은 목표·결과·점수·기준·EP·확인, 실패 팝업은 목표·결과·미충족 이유·초기화/복구·남은 횟수·재시도로 구성한다.

### 6.5 콘텐츠 생성·검수

1. 학습 주제·목표 조건·원본 이미지 확정.
2. LLM으로 정답 조건, 부분 충족, 충돌·주의 분산 키워드 후보 생성.
3. 스키마·중복 의미·대상 연결·목표 학습 요소를 코드로 검사, 운영자가 검수.
4. 원본을 참조해 일부 조건만 바꾼 유사 결과 제작. 이미지별 실제 조건·제작 모델·프롬프트·버전 기록.
5. GenEval/TIFA의 세부 조건 점검 원리를 참고해 개수·색·관계 등을 검수. 원본과 거리 하나만으로 승인하지 않음.
6. 성공·실패·고성능 경계·충돌·누락·최소 예산 조합 확인 → 승인 버전 발행.

초기에는 소수의 목표와 명확한 대표 조건군으로 시작한다. 신규 이미지 제작은 사용자 요청과 분리된 CLI 작업으로 수행하고, 자동 생성 결과를 자동 공개하지 않는다.

## 7. 프롬프트 개선기

Kiro의 명시적 개선·검토 UX를 참고하며 별도 Gemini 프롬프트와 구조화 응답으로 구현한다. Kiro 비공개 내부 로직이나 공개 호출 API를 사용한다는 전제로 개발하지 않는다.

입력 예시: `학교 발표용 재활용 방법 3개 추천좀`.

응답은 다음을 분리한다.

- `improvedText`: 원문 목적·수량·맥락을 보존해 정리한 개선안.
- `extendedExample`: 대상·형식 등 추가 조건을 붙인 구체적인 예시.
- `addedAssumptions`: 원문에 없던 ‘초등학생’, ‘쉬운 말’, ‘한 문장’ 같은 조건을 명시.
- `changes`: 무엇을 바꿨는지 짧게 설명.
- `tips`: 연결 구절 ID·인용·설명. 텍스트 수정 후 위치가 달라지면 다시 계산하거나 해당 팁 연결 해제.
- `taskProfile`: 추천에 재사용할 작업 유형·필요 기능·복잡도·정보 부족 여부.

원문이 정하지 않은 조건을 사용자가 이미 요청한 사실처럼 설명하지 않는다. PDF의 ‘쉬운 말·한 문장’ 등은 제안 조건임을 표시하도록 개발 시 예시 설명을 다듬는다. 모든 입력에 역할·예시·장문 구조를 강제로 추가하지 않는다.

텍스트 탭 + 짧은 밑줄, 결과 상자 우측 하단 편집·복사 아이콘, 연결 구절 선택 시 말풍선. 사용자가 편집한 문장이 모델 추천 입력이다. 원문과 결과가 항상 토큰·비용을 줄인다고 주장하지 않는다. 개선문을 실제 AI 서비스에 자동 제출하지 않는다.

호출: 서버에서 길이·일일 한도 검사 → idempotent 작업 생성 → Gemini 구조화 출력 → Zod 검증 → 성공 저장·사용량 확정. 긴 요청은 작업 조회 방식으로 복구하며 메모리 내 작업 상태만 사용하지 않는다. 외부 응답 대기는 DB 트랜잭션 밖에서 처리한다.

## 8. AI 모델 추천

### 8.1 입력·표시 계약

R01은 문장 입력과 나란한 원형 전송 버튼을 사용한다. 결과는 입력 아래 텍스트로 ‘요약 업무에는 Light를 추천해요’처럼 표시한다. Light/Medium/High 상자를 누르면 하단 시트에서 여러 모델을 탐색한다. 검색은 모델명·제공사 대상이며 행은 모델명 왼쪽, 제조사 오른쪽, 추천 표시를 제조사 옆에 둔다. 텍스트는 세로 중앙 정렬.

상세 화면은 종합 성능 → 속도·첫 답변 토큰 → 입력·출력 100토큰당 USD → 업무 관련 공개 벤치마크 2~3개 → 출처·설정·갱신일·미측정 안내다. 예상 총비용 상자, 임의 적합도 %, 다른 모델 보기·문장 복사 버튼은 제외한다. 미측정은 N/A이며 0점으로 바꾸지 않는다.

### 8.2 추천 처리

1. 직접 입력은 제한된 분석 호출, 동일 개선문은 문장 해시·분석 버전 검증 후 분석 재사용.
2. 컨텍스트·입력 모달리티·지원 기능·활성 여부로 후보 필터.
3. 작업에 관련된 벤치마크와 정책상 최소 성능을 충족하는 모델만 추천 후보로 남김.
4. 내부 동일 입출력 가정에서 비용을 비교해 가장 저렴한 후보를 선정. 유사 비용이면 낮은 운영 등급·응답 속도 등의 고정 tie-break 사용.
5. 해당 모델의 등급을 Light/Medium/High로 안내하고 나머지 모델도 탐색 가능하게 함.

```text
eligible(m) = capabilityMatch(m) && contextFits(m)
              && taskQualityEvidence(m) >= policyThreshold(task)
estimatedCost(m) = assumedInputTokens * promptPricePerToken
                   + assumedOutputTokens * completionPricePerToken
recommendation = argmin(estimatedCost(m)) among eligible models
```

성능 부족한 후보를 단지 싸다는 이유로 추천하지 않는다. 성능 자료가 부족하면 추천 불가·근거 부족 상태를 반환하고 객관적 지표 목록만 제공한다. 종합 지수·다른 척도의 점수를 임의 평균 내지 않는다. 업무 기준과 등급 분류는 **자체 정책**이며 벤치마크 제공자의 공식 등급이나 품질 보장이 아니다.

추천 계산에 사용한 출력 길이 가정과 정책은 서버 기록으로 남긴다. UI는 요청별 예상 총비용을 표시하지 않고 단가를 표시한다. 실제 답변 생성이나 여러 모델 동시 호출은 없다. RouteLLM의 품질·비용 고려 원리를 참고한 자체 추천이며 RouteLLM 배포나 OpenRouter Auto 실호출은 필수 아님.

### 8.3 지표 수집과 출처

- OpenRouter 모델 목록: `GET /api/v1/models`. 모델 ID·가격 단위·context_length·입력 모달리티 등 제공 필드만 매핑.
- Artificial Analysis: Free와 상위 플랜의 제공 범위를 구분한다. Free 조회 경로 `/api/v2/language/models/free`를 기준으로 실제 계정 응답 스키마 확인. 개별 벤치마크 전체가 무료 API에 있다고 가정하지 않는다.
- 모델·버전·추론 설정을 정확히 매핑한다. 제조사 표시명은 하드코딩한 모델명 추측만으로 생성하지 않는다.
- PDF의 IFBench 31.5%, AA-LCR 32.0% 등은 특정 설정·조회일의 목업 예시다. 운영 DB 초기값으로 무검증 복사하지 않는다.
- API가 제공하지 않는 개별 지표는 사용 권한·재배포 조건을 확인한 검수 데이터로 추가하거나 미제공 처리한다. 공개 웹표 크롤링을 기본 계약으로 삼지 않는다.
- 100토큰 단가는 원본 per-token 값 ×100, USD 기준. 환율 연동은 1차 제외.

주간 GitHub Actions + 수동 실행으로 수집 → staging snapshot 검증 → 활성 버전 원자적 교체. 실패 시 마지막 정상 스냅샷 유지. 추천 응답은 하나의 snapshot/policy 버전만 사용한다. 호출 때마다 외부 모델 API를 조회하지 않는다.

## 9. 정원·상점·소셜

정원 예시는 진한 단색 배경과 캐릭터 한 명, 울타리·장식으로 구성한다. 정원 영역 우측 아래 작은 연필 버튼으로 편집 진입한다. 보유 장식만 제한된 배치 영역에 놓고 저장한다. 초기 구현은 좌표 스냅 방식 제안. 성장 타이머·물주기·방치 페널티는 제외한다.

캐릭터 상점과 정원 상점 진입은 정사각형 상점 그림 버튼 두 개, 그 아래 소셜 버튼. 상품 목록은 모바일 2열. 상품 탭 → 미리보기·가격·구매 후 잔액 확인 → 구매 확정. 소유 캐릭터는 선택하면 정원과 모든 게임에 적용한다. 별도 캐릭터 보관함 탭·하단 중복 구매 버튼·게임 테마 구매는 없다.

소셜 문구: **내 코드 SLOP-1234 / 코드 복사 · 코드로 친구 추가 · 미니앱 초대**. 코드는 표시 예시이며 서버가 충돌 없는 코드를 발급한다. 세 동작은 각각 누를 수 있는 액션으로 구현한다.

- 코드 복사: 공식 지원 클립보드 기능으로 자기 코드 복사.
- 코드로 친구 추가: 입력 → 대상 최소 프로필 → 요청 → 상대 수락. 자신·차단·중복 관계 검사.
- 미니앱 초대: 공식 `getTossShareLink`·`share` 흐름을 사용해 토스 안의 AIMI로 연결. 외부 앱 다운로드·자사 랜딩 링크 없음.
- 토스 친구 목록 자동 취득 아님. 자체 DB 친구 관계다.
- 친구별 캐릭터·공개 챌린지 상태·정원 방문 표시. 원문·개선 결과·개인 호출량은 공개하지 않음.
- 초대 링크는 단기 불투명 토큰을 사용하고 도착 후 로그인·미리보기·수락으로 연결. 토큰만으로 친구 관계를 강제 생성하지 않음.
- 친구 삭제·차단·비공개 전환은 서버에서 접근을 차단한다. 탈퇴 시 초대·공개 정원 접근도 정리한다.

## 10. 서버·DB·API 계약

### 10.1 계정과 권한

토스 로그인 인증 코드를 백엔드에 전달하고 공식 서버 인증 방식으로 내부 user_id에 연결한다. 필요한 토스 서버 API 인증서·키는 서버에만 둔다. 앱 요청은 서버 발급 세션으로 인증한다. Google·Apple·이메일 로그인 UI는 추가하지 않는다.

서버 전용 DB 경로에서 모든 사용자·소유권을 검사한다. 브라우저에 Supabase service-role 키를 넣지 않는다. 직접 접근하는 테이블이 있다면 별도 RLS·세션 매핑 설계를 마친 뒤 허용한다. Storage 공개 경로에는 승인된 미션 에셋만 둔다. 친구 전용 데이터는 서버 권한 검사 후 반환한다.

날짜·상태·사용자·버전·외래키는 정규 컬럼, 의미 조건·레이아웃은 검증한 JSONB로 저장한다. 규칙·가격·보상 정책·결과 이미지 버전은 시도 기록에 참조해 과거 결과를 재현한다.

### 10.4 트랜잭션과 복구

- EP와 구매: DB 트랜잭션 또는 Postgres 함수로 잔액 확인·원장·보유품을 한 번에 확정. HTTP 요청 여러 개로 따로 갱신하지 않는다.
- 게임 종료: 발급 play_id·시드·버전·경과 시간·이벤트로 기록을 검증, 동일 완료 요청은 기존 결과 반환. 임의 score 숫자만 신뢰하지 않는다.
- 제출: 콘텐츠·이미지 매칭 검증 후 진행 상태를 잠그고 남은 횟수·예산을 다시 확인, 시도·성공·EP 원장을 함께 확정.
- 동시 요청 두 개가 마지막 횟수나 잔액을 동시에 쓰지 못하도록 잠금·조건부 갱신 적용.
- 네트워크 응답 유실은 결과 재조회로 복구. 사용자가 다시 누른다고 실패·EP가 중복 생성되지 않음.
- 정원 편집은 revision 비교로 오래된 탭의 덮어쓰기 방지.
- LLM 작업은 DB 상태 queued/running/succeeded/failed + lease/timeout. 별도 Redis 없이 단일 서버의 복구 가능한 작업 루프를 제안. 서버 재시작 후 만료 작업 처리 기준을 둔다.

### 10.5 제한과 데이터 최소화

사용자별 개선·분석 일일 한도, 서비스 전체 지출 상한, 입력 길이·최대 출력, 타임아웃을 서버 설정으로 둔다. **PDF의 ‘오늘 4회 남음’은 표시 예시이며 호출 한도 확정 아님.** 재시도는 제한된 횟수만 허용하고 사업자 API 실패를 무제한 재호출하지 않는다.

개선·추천 원문은 사용자에게 필요한 기간만 보존한다. 개발용 기본안은 원문·응답 24시간 임시 보관 후 삭제, 토큰·모델·상태·비용 메타데이터 분리 보존이며 실제 기간은 동의·처리방침 작성 전 확정한다. 로그에는 프롬프트·인증 코드·키를 기본 기록하지 않는다. 실제 API 사용량 원장은 내부 운영용이며 사용자 외부 채팅 사용량과 연결하지 않는다.

## 11. 콘텐츠 교체·배포·환경변수

미리 승인한 날짜별 콘텐츠를 서버가 한국 날짜로 조회한다. 자정마다 앱 패치나 GitHub Actions 실행이 필요한 구조가 아니다. 예정 콘텐츠가 없으면 검수된 fallback 반환. 게임·규칙 버전이 바뀌면 진행 중 세션은 원래 버전을 유지한다.

구분: 목표·키워드·가격·상점 품목·팁·모델 스냅샷 변경은 검증한 DB/Storage 등록. 새 게임 코드·화면·SDK 변경은 클라이언트 배포와 필요한 검수. API 로직 변경은 서버 배포. 모델 데이터 갱신과 이미지 제작 작업은 별도다.

환경변수 이름 제안:

```text
# 미니앱: 비밀 아님
VITE_API_BASE_URL
# 서버: 클라이언트에 주입 금지
DATABASE_URL
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
GEMINI_API_KEY
GEMINI_TEXT_MODEL
SESSION_SIGNING_KEY
TOSS_CLIENT_CERT_PATH
TOSS_CLIENT_KEY_PATH
CORS_ALLOWED_ORIGINS
OPTIMIZER_DAILY_LIMIT
RECOMMENDATION_DAILY_LIMIT
LLM_REQUEST_TIMEOUT_MS
# 수집 작업 전용
ARTIFICIAL_ANALYSIS_API_KEY
OPENROUTER_API_KEY
MODEL_SYNC_DATABASE_URL
```

구체적인 토스 인증 방식·필드명은 공식 SDK/서버 문서를 확인해 맞춘다. 위 이름은 프로젝트 내부 제안이다. 키·인증서를 Git에 넣지 않는다. CORS는 실제 출시·테스트 도메인을 확인해 제한한다.

제안 구조:


| 순서 | 개발 단위 | 인수 조건 |
|---|---|---|
| 1 | 공통 UI·목업 API | 최신 6슬라이드 흐름, 작은 기기 스크롤·키보드·팝업·시트 확인 |
| 2 | 로그인·DB·경제 | 토스 계정 연결, 중복 보상·동시 구매 방지, EP 단위 분리 |
| 3 | 길 건너기 + 이미지 과제 1개 | 기록→예산→조합→조건 판정→성공 EP→재조회가 실제 DB에서 완결 |
| 4 | 정원·상점·캐릭터·소셜 | 선택 1명 통일, 소유권·잔액·배치 저장, 코드 요청·수락·방문·차단 |
| 5 | 개선기 | 의도 보존·추가 조건 구분·팁 연결·편집·복사·추천 인계·한도·오류 복구 |

| 7 | Temple Run·다이노 및 일일 일정 | 같은 캐릭터·기록 API 사용, 하루 한 게임, 서로 다른 게임 비교 랭킹 없음 |

프론트/서버 담당이 달라도 packages/contracts와 이 명세를 먼저 공유한다. 화면마다 별도 임시 EP 지갑이나 서로 다른 사용자 ID를 만들지 않는다. 기존 팀원 프로젝트를 재사용할 때는 실제 소스·의존성·API 계약을 확인하며 APK만으로 통합을 전제하지 않는다.

핵심 검증: 두 종류 5회 제한·모델 임계값 경계·필수 조건·콘텐츠 오류 복구, 중복/동시 거래, 같은 캐릭터 적용, 모바일 키워드 선택·순서 변경, 원문 수정 후 분석 재사용 방지, 데이터 미제공 처리, 로그인 후 초대 복귀, 차단·비공개 정원 접근 방지.

## 13. 개발 시작 전에 확정할 최소 항목

1. **게임 방식:** 2D/2.5D 채택 여부, 최고 기록 집계·예산 환산·코인 EP 상한·중단/자정 유예.
2. **과제:** 첫 목표, 키워드 수·비용, 모델 비용·임계값, 필수/충돌/누락 감점, 승인 결과 이미지 커버리지.
3. **경제:** 출석·팁·개선기·성공 보상 수치, 성공 하루 1회 정책, 상품 초기 가격.
4. **AI 운영:** Gemini 실제 사용 가능 모델·입출력 한도·일일 호출수·지출 상한·원문 보존 기간.
5. **추천 근거:** 사용할 AA 플랜·실제 제공 지표, 모델 버전 매핑, 업무별 최소 성능·등급 정책.
6. **플랫폼:** 게임/비게임 분류, AI 콘텐츠 안내, 내비게이션·공유·탈퇴 등 공식 요구의 실제 적용.

전체 UI를 다시 논의할 필요는 없다. 위 항목은 설정·검증 결정을 남긴 것으로, UX 확정과 기술적 검증 완료를 구분하기 위한 목록이다.
