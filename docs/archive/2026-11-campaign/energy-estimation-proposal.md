# 토큰·모델 사용량 기반 에너지 추정안

작성일: 2026-10-19 (한국 시간). **설계 제안이며 현재 앱에 에너지 계산이나 임의 계수를 적용하지 않았다.**

## 권장 방향

영수증에는 모델 API가 반환한 토큰을 실제 사용량으로 표시한다. 에너지는 이와 별개로 **공개 벤치마크를 기준으로 한 시나리오 추정 에너지(Wh)**라고 표시한다. Gemini API 서버의 실측값이라고 표현하지 않는다.

생성과 판정을 각각 계산한 뒤 챌린지 전체를 합산한다. 모델, 모델 버전, 작업 종류와 계수 근거가 다른 요청에 동일한 J/token 상수를 적용하지 않는다. Render에는 작은 계수 JSON과 산술 계산만 넣으며, GPU·CLIP·torch나 벤치마크 실행 환경을 올리지 않는다.

## 연구에서 가져올 부분

[ML.ENERGY 논문, 특히 2.3·3.2절](https://arxiv.org/html/2505.06371)은 전체 응답 단위의 에너지 회계를 우선하고, LLM에서는 정상상태의 에너지/생성 토큰 비율로 요청에 에너지를 배분한다. 이 비율은 해당 모델·하드웨어·배치·워크로드 조건의 값이다. 논문의 diffusion 결과는 이미지 요청 단위로 회계하며, 이를 Gemini 이미지 생성 모델의 실측 계수로 취급하면 안 된다.

[공식 Data & Toolkit](https://ml.energy/data/)은 H100/B200의 LLM·diffusion 실행 데이터를 제공하며 모델·GPU·작업별로 결과를 필터링할 수 있다. 데이터 접근은 Hugging Face 승인과 토큰이 필요하다. 현재 조사에서는 원자료를 내려받거나 Gemini용 계수를 검증하지 않았다.

[Google의 운영 환경 측정 연구](https://arxiv.org/html/2508.15734)는 가속기 외 CPU·DRAM, 유휴 용량, 데이터센터 오버헤드까지 측정 경계에 포함한다. 여기의 Gemini Apps 텍스트 요청 중앙값 0.24 Wh는 특정 서비스·시점의 값으로, 현재 API의 이미지 생성이나 이미지 비교 한 건에 대입할 수 없다.

## 계산 단위와 범위

- 기본 표시는 Wh. J를 사용하는 계수는 합산 후 3600으로 나눠 변환한다. 1 Wh = 3600 J.
- GPU 기준 프로필이면 결과도 가속기 범위로 한정한다. 이를 데이터센터 전체 전력량으로 표시하지 않는다.
- 전체 서비스 에너지를 확장 추정하려면 CPU·메모리·유휴 용량·PUE의 별도 가정이 필요하다. 이미 전체 범위를 포함한 프로필에 PUE를 다시 곱하지 않는다.
- Render의 HTTP 응답 시간에는 대기열·네트워크 시간이 포함된다. `71초 × GPU 정격전력`처럼 계산하지 않는다.
- 출력 토큰에 추론 토큰이 포함되는지는 공급자 메타데이터 정의를 확인한다. 입력·출력·추론·total을 모두 더하지 않는다. total은 검산에 사용한다.

## 단계 1: 가장 작은 시나리오 추정

### 판정 모델

ML.ENERGY 방식과 일치하는 기준 프로필을 고르면 다음과 같이 출력 토큰에 배분할 수 있다.

```text
κ_reference = 기준 실행의 정상상태 에너지(J) / 정상상태 생성 토큰 수
E_router_reference(J) = κ_reference × 해당 요청의 생성 토큰 수
```

이 κ에는 기준 실행의 입력 처리 비용이 이미 배분되어 있으므로 입력 토큰 비용을 임의로 또 더하지 않는다. 짧은 JSON 답변과 두 장의 이미지 입력이 있는 현재 Router는 입력 비중이 크다. 따라서 일반 텍스트 대화 프로필 하나를 사용하는 값은 정확도가 낮은 참고 시나리오로만 취급한다.

같은 모델·GPU·작업에 대해 배치 조건별 κ를 보존하고, 선택한 낮음/기준/높음 시나리오를 각각 계산한다. 이 범위는 Gemini 실제값을 포함한다고 보장하는 신뢰구간이 아니다.

### 이미지 생성 모델

이미지 생성 토큰은 텍스트 생성 토큰과 같은 연산 단위라고 가정할 수 없다. 권장 기본형은 다음과 같다.

```text
E_image_reference(J) = 입력 처리 추정치 + 해상도·품질별 J/이미지 × 생성 이미지 수
```

100% 토큰 기반 표시가 꼭 필요하면, 동일 이미지 작업 프로필에서 얻은 다음 환산을 실험용으로 사용할 수 있다.

```text
κ_image_reference = 기준 J/이미지 / 기준 이미지 출력 토큰 수
E_image_reference(J) = 입력 처리 추정치 + κ_image_reference × 이미지 출력 토큰 수
```

이 경우 이미지 해상도·모델·출력 토큰 정의가 고정되어야 한다. 공개 diffusion 기준값과 Gemini 토큰의 결합은 교차 모델 시나리오이지 Gemini 보정 결과가 아니다. 현재 Gemini에 적용 가능한 계수가 확보된 상태는 아니다. 계수가 없으면 0 Wh 대신 ‘산정 근거 미확보’를 반환한다.

## 단계 2: 입력·출력·모달리티를 구분한 모델

추가 실측 자료에서 입력 크기와 출력 크기를 독립적으로 바꾼 실행을 확보할 수 있으면 다음과 같은 회귀를 검토한다. 이는 논문의 식을 그대로 인용한 것이 아니라 앱을 위한 제안이다.

```text
E_call(J) = c_m
          + a_m × 텍스트 입력 토큰
          + b_m × 이미지 입력 토큰
          + d_m × 텍스트 출력 토큰
          + e_m × 이미지 출력 토큰
          + f_m × 추론 토큰

E_session(Wh) = Σ E_call(J) / 3600
```

`m`은 API 모델 이름만이 아니라 기준 모델·버전·작업·하드웨어·배치·측정 범위를 포함한다. 입력/출력 토큰 항목은 서로 배타적으로 정규화해야 한다. 출력 토큰 비례로 배분된 요청 에너지 자체를 정답으로 삼아 입력 계수를 회귀하면 입력 비용을 독립적으로 식별할 수 없다. 독립적인 실행/실측 자료가 없으면 세분 계수를 만들어 내지 않는다.

계수는 비음수 회귀 등으로 추정하고 실행 단위로 학습/평가를 분리한다. 기준 환경에서의 오차를 검증하더라도 Gemini로 옮길 때의 오차까지 검증한 것은 아니다.

## 현재 DB로 가능한 것과 필요한 것

이미 확보된 값:

- `api_calls`: 실제 공급자·모델 버전, 생성/판정 작업 구분, 성공/오류 상태, 입력·출력·추론·총 토큰, 원본 `usage_metadata`.
- `successes`: 첫 PASS까지 모델별·전체 누적값. FAIL과 실제 전송된 오류 요청도 원장에 남는다.
- `attempts`: 원문 프롬프트, Router 판정과 이유.

추가할 후보:

- 메타데이터의 모달리티별 토큰 세부 내역 정규화. 항목이 없으면 총 입력을 텍스트와 이미지로 임의 분할하지 않는다.
- 생성 이미지 수, 출력 해상도, 이미지 모델 설정. 이미지 생성 성공 시 실제 결과에서 기록한다.
- 에너지 기준 프로필: 기준 모델/하드웨어/배치/작업/범위, 출처 URL, 데이터 버전, 계수 단위, 적용 조건.
- 추정 결과: 프로필 버전, 시나리오별 Wh, 누락 호출 수, 적용된 모델 목록과 입력 스냅샷 해시.

시간 초과·오류 요청은 실제 계산이 있었을 수 있다. 토큰 누락을 0으로 바꾸지 않는다. 모든 호출에 추정치가 없으면 합산값을 ‘전체 에너지’라고 부르지 않고, 산정 가능한 부분과 미확인 요청 수를 별도로 보존한다.

## 구현 순서

1. 원본 `usage_metadata`에 필요한 모달리티 구분이 실제로 있는지 표본을 확인한다. 이 단계는 운영 데이터 읽기만으로 가능하다.
2. 별도 분석 환경에서 승인받은 ML.ENERGY 데이터를 준비하고 적합한 기준 프로필과 조건을 선정한다. 사용할 수 없는 Gemini 매핑은 명시적으로 비워 둔다.
3. 검토가 끝난 계수만 작은 버전 관리 JSON으로 내보낸다. 임의 기본 계수는 두지 않는다.
4. 서버 순수 계산 함수로 요청별·모델별·세션별 추정치를 계산하고 누락과 단위를 검사한다. 잘못된 모달리티, 프로필 없는 모델 버전, 토큰 누락, 중복 합산을 테스트한다.
5. 결과는 예를 들어 `energy_estimates(receipt_id, profile_version, scope, scenario_values, coverage, inputs_hash)`처럼 영수증과 연결된 별도 스냅샷에 보존한다. 기존 첫 PASS 기록을 덮어쓰지 않는다. 스키마와 SQL은 이 단계에서 별도로 작성하고 사용자가 적용한다.
6. 영수증에는 ‘벤치마크 기준 추정 에너지: [범위] Wh’ 한 줄만 표시한다. 계수 출처·측정 경계·누락 정보는 설명 문서/내부 기록으로 보존한다. 프로필 변경 후 재계산은 새 버전으로 남겨 재출력 값이 몰래 바뀌지 않게 한다.

## 현재 작업의 경계

판정 이유와 모델별 토큰 합계는 구현한다. 이 문서의 에너지 추정은 다음 단계 제안이다. 추가 SQL·GPU 계측·에너지 관련 API 호출은 이번 작업에 포함하지 않는다.
